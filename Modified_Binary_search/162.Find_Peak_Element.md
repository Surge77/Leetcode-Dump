# 🔹 Problem Name: 162. Find Peak Element (Binary Search on Slope, Medium)

**🔗 Link:** [LeetCode 162](https://leetcode.com/problems/find-peak-element/)
**🟢 Status:** 🔄 Need Review

## 🔹 Quick Breakdown

* **Difficulty Level:** Medium
* **Main Approach:** **Binary search on the slope.** Compare `nums[mid]` with `nums[mid + 1]`. Going up (`nums[mid] < nums[mid + 1]`) → a peak exists to the right, `lo = mid + 1`. Going down → a peak exists at `mid` or to its left, `hi = mid`. When `lo == hi`, it is a peak.
* **Core Concept:** binary search does not need a sorted array — only a rule that guarantees an answer survives in the half you keep
* **When to Use This Pattern?** "Find **any** local max/min", bitonic / mountain arrays, unimodal functions.
* **Mistakes to Avoid:**
  * Thinking you must find the global maximum — any peak is accepted.
  * Comparing with `nums[mid − 1]` and `nums[mid + 1]` both and getting lost at the borders; one neighbour is enough.

## 🔹 Optimization Path

* **Brute Force:** linear scan for the first `i` with `nums[i] > nums[i + 1]` (or the last index) — O(n).
* **Optimized Solution:** binary search on the slope — O(log n), as required.
* **Further Improvements Possible?** No.

## 🔹 Solution Breakdown

* **Optimal Approach:** `lo, hi = 0, n − 1`; while `lo < hi`: `mid = (lo + hi) // 2` (so `mid + 1 ≤ hi` is valid); move as above; return `lo`.
* **Why This Works?** `nums[−1] = nums[n] = −∞` and neighbours are never equal. If `nums[mid] < nums[mid + 1]`, walk right from `mid + 1`: the values cannot rise forever because the right border is `−∞`, so the first drop is a peak in `[mid + 1, hi]`. Symmetrically, `nums[mid] > nums[mid + 1]` guarantees a peak in `[lo, mid]`. The kept range always contains a peak and always shrinks.
* **Edge Cases Considered:**
  * `n = 1` → `0`.
  * Strictly increasing → `n − 1`; strictly decreasing → `0`.
  * Values at `−2³¹` — the `−∞` borders are conceptual, never compared, so no sentinel overflow issue.

* **Belongs To:** Modified Binary Search — search on a monotone predicate that is not the array order

## 🔹 Tricks & Patterns Used

* **Compare `mid` with `mid + 1`:** `lo < hi` makes `mid < hi`, so the neighbour always exists.
* **Keep the half that provably contains an answer** rather than the half that "contains the target".

## 🔹 Alternative Data Structures

* None; ternary search would also work on a unimodal array but not on this multi-peak one.

## 🔹 Complexity Analysis

* **Time Complexity:** O(log n)
* **Space Complexity:** O(1)

## 🔹 Code Snippet (Brute Force)

```python
from typing import List


class Solution:
    def findPeakElement(self, nums: List[int]) -> int:
        for i in range(len(nums) - 1):
            if nums[i] > nums[i + 1]:
                return i  # nums[i] > nums[i - 1] too, otherwise we would have stopped earlier
        return len(nums) - 1
```

## 🔹 Code Snippet (Optimized)

```python
from typing import List


class Solution:
    def findPeakElement(self, nums: List[int]) -> int:
        lo, hi = 0, len(nums) - 1
        while lo < hi:
            mid = (lo + hi) // 2
            if nums[mid] < nums[mid + 1]:
                lo = mid + 1  # rising: the right border is -inf, so a peak lies ahead
            else:
                hi = mid
        return lo
```
