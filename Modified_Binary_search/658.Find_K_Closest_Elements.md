# 🔹 Problem Name: 658. Find K Closest Elements (Binary Search on Window Start, Medium)

**🔗 Link:** [LeetCode 658](https://leetcode.com/problems/find-k-closest-elements/)
**🟢 Status:** 🔄 Need Review

## 🔹 Problem Statement

Given a sorted array `arr`, a count `k` and a value `x`, return the `k` elements closest to `x`, in ascending order. When two elements are equally close to `x`, the smaller one is preferred.

* **Example:** `arr = [1,2,3,4,5], k = 4, x = 3` → `[1,2,3,4]`
* **Constraints:** `1 ≤ k ≤ arr.length`; `1 ≤ arr.length ≤ 10^4`; `arr` is sorted ascending; `-10^4 ≤ arr[i], x ≤ 10^4`.

## 🔹 Quick Breakdown

* **Difficulty Level:** Medium
* **Main Approach:** **Binary search for the left edge of the answer window.** In a sorted array the `k` closest elements are a contiguous block `arr[i : i + k]`. Search `i` in `[0, n - k]`: compare `x - arr[mid]` with `arr[mid + k] - x` to decide whether the window should slide right.
* **Core Concept:** the closest `k` values form a window, so search over window starts instead of over elements
* **When to Use This Pattern?** Nearest-`k` in a sorted array, "best contiguous block" where moving the block one step right is a local, comparable decision.
* **Mistakes to Avoid:**
  * Searching `hi = n - 1` and reading `arr[mid + k]` out of bounds — the start is at most `n - k`.
  * Breaking ties the wrong way: on equal distance the **smaller** value wins, so a tie must not move the window right.
  * Returning elements by index distance instead of value distance.

## 🔹 Optimization Path

* **Brute Force:** sort all elements by `(|a - x|, a)`, take the first `k`, sort them back — O(n log n).
* **Optimized Solution:** binary search on the window start — O(log(n − k) + k).
* **Further Improvements Possible?** The `k` in the cost is just copying the output; nothing better is possible.

## 🔹 Solution Breakdown

* **Optimal Approach:** `lo, hi = 0, n - k`. For `mid`: if `x - arr[mid] > arr[mid + k] - x`, the left element is farther than the element just past the window, so `lo = mid + 1`; else `hi = mid`. Return `arr[lo:lo + k]`.
* **Why This Works?** Windows `[mid, mid + k)` and `[mid + 1, mid + k + 1)` differ by dropping `arr[mid]` and adding `arr[mid + k]`. The better window is the one that keeps the closer of those two, and that comparison is monotone along the sorted array.
* **Edge Cases Considered:**
  * `x` smaller than every element → `lo` ends at `0`; larger than all → `lo` ends at `n - k`.
  * `k == n` → range is a single point, return the whole array.
  * Ties (`x - arr[mid] == arr[mid + k] - x`) keep the left window, matching the "smaller value" rule.

## 🔹 Tricks & Patterns Used

* **Compare the two elements that differ** between adjacent windows rather than recomputing window quality.
* **`hi = n - k`** keeps `mid + k` always valid.

## 🔹 Alternative Data Structures

* Binary search for `x`, then expand two pointers outward — O(log n + k).
* Max-heap of size `k` keyed by distance — O(n log k), ignores the sorted order.
* Two pointers shrinking from both ends, dropping the farther of `arr[left]` / `arr[right]` until `k` remain — O(n − k).

## 🔹 Complexity Analysis

* **Time Complexity:** O(log(n − k) + k)
* **Space Complexity:** O(1) beyond the output

## 🔹 Code Snippet (Brute Force)

```python
from typing import List


class Solution:
    def findClosestElements(self, arr: List[int], k: int, x: int) -> List[int]:
        by_closeness = sorted(arr, key=lambda value: (abs(value - x), value))
        return sorted(by_closeness[:k])
```

## 🔹 Code Snippet (Optimized)

```python
from typing import List


class Solution:
    def findClosestElements(self, arr: List[int], k: int, x: int) -> List[int]:
        lo, hi = 0, len(arr) - k
        while lo < hi:
            mid = (lo + hi) // 2
            if x - arr[mid] > arr[mid + k] - x:
                lo = mid + 1  # arr[mid] is strictly farther than arr[mid + k]
            else:
                hi = mid  # ties keep the smaller values
        return arr[lo:lo + k]
```
