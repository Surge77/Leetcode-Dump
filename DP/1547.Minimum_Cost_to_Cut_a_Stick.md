# 1547. Minimum Cost to Cut a Stick

**🔗 Link:** [LeetCode 1547](https://leetcode.com/problems/minimum-cost-to-cut-a-stick/)
**🟢 Status:** 🔄 Need Review


## 🔹 Problem Statement

A stick of length `n` is marked at integer positions `0..n`, and `cuts` lists the positions where it must be cut. The cuts may be done in any order; each cut costs the current length of the piece being cut. Return the minimum total cost over all orderings.

* **Example:** `n = 7, cuts = [1,3,4,5]` → `16`
* **Constraints:** `2 ≤ n ≤ 10^6`, `1 ≤ cuts.length ≤ min(n - 1, 100)`, all `cuts[i]` distinct and in `[1, n - 1]`

## 🔹 Quick Breakdown

* **Difficulty Level:** Hard
* **Main Approach:** **Interval DP over cut positions.** Sort the cuts and add the ends: `pos = [0] + sorted(cuts) + [n]`. `dp[i][j]` = min cost to make every cut strictly between `pos[i]` and `pos[j]`. Choose the **first** cut `k` in that piece: it costs the piece length `pos[j] − pos[i]`, then the two halves are independent: `dp[i][j] = pos[j] − pos[i] + min over i<k<j of (dp[i][k] + dp[k][j])`.
* **Core Concept:** "which split happens first" interval DP — same shape as Burst Balloons (which picks the **last** one)
* **When to Use This Pattern?** An operation on a segment splits it into two independent segments and its cost depends on the current segment — cutting sticks, merging stones, matrix-chain multiplication, polygon triangulation.
* **Mistakes to Avoid:**
  * DP over stick coordinates (`n` up to 10⁶) — index by the ≤ 102 cut positions instead.
  * Forgetting to sort `cuts`.
  * Greedy (cut the middle first / cheapest first) — not optimal in general.

## 🔹 Optimization Path

* **Brute Force:** recursion trying every cut as the first one, no memo — exponential (Catalan-like).
* **Optimized Solution:** interval DP — O(c³) with `c ≤ 100` cuts ≈ 10⁶ operations.
* **Further Improvements Possible?** Knuth's optimisation applies (the cost is a quadrangle-inequality interval length), giving O(c²); unnecessary for `c ≤ 100`.

## 🔹 Solution Breakdown

* **Optimal Approach:** fill `dp` by increasing gap `j − i`; `dp[i][i + 1] = 0` (no cut inside).
* **Why This Works?** Whatever order is used, some cut inside `(pos[i], pos[j])` is made first and costs the full piece; afterwards the left and right pieces never interact, so each is solved optimally on its own.
* **Edge Cases Considered:**
  * One cut → `n`.
  * Cuts given unsorted.

## 🔹 Tricks & Patterns Used

* **Add sentinels `0` and `n`** so every piece is `(pos[i], pos[j])`.
* **Compress coordinates to cut indices** — complexity depends on the number of cuts, not the length.

## 🔹 Alternative Data Structures

* Top-down `f(i, j)` with `lru_cache` — same O(c³), recursion depth ≤ 102.

* **Time Complexity:** O(c³) (plus O(c log c) sort)
* **Space Complexity:** O(c²)

## 🔹 Code Snippet (Brute Force)

```python
from typing import List


class Solution:
    def minCost(self, n: int, cuts: List[int]) -> int:
        def cost(lo: int, hi: int, inside: List[int]) -> int:
            if not inside:
                return 0
            return hi - lo + min(
                cost(lo, cut, [c for c in inside if c < cut]) + cost(cut, hi, [c for c in inside if c > cut])
                for cut in inside)

        return cost(0, n, cuts)
```

## 🔹 Code Snippet (Optimized)

```python
from typing import List


class Solution:
    def minCost(self, n: int, cuts: List[int]) -> int:
        pos = [0] + sorted(cuts) + [n]
        m = len(pos)
        dp = [[0] * m for _ in range(m)]
        for gap in range(2, m):
            for i in range(m - gap):
                j = i + gap
                dp[i][j] = pos[j] - pos[i] + min(dp[i][k] + dp[k][j] for k in range(i + 1, j))
        return dp[0][m - 1]
```
