# 142. Linked List Cycle II

**🔗 Link:** [LeetCode 142](https://leetcode.com/problems/linked-list-cycle-ii/)
**🟢 Status:** 🔄 Need Review


## 🔹 Problem Statement

Given the head of a singly linked list, return the node where its cycle begins, or null if the list has no cycle. The cycle's position `pos` is only used by the judge to build the input, and the list must not be modified.

* **Example:** `head = [3,2,0,-4], pos = 1` → the tail connects to node index 1 (the node with value `2`)
* **Constraints:** nodes in `[0, 10^4]`; `-10^5 ≤ Node.val ≤ 10^5`; `pos` is `-1` or a valid index. Follow-up: use `O(1)` memory.

## 🔹 Quick Breakdown

* **Difficulty Level:** Medium
* **Main Approach:** **Floyd's cycle detection, phase 2.** Run `slow` (1 step) and `fast` (2 steps) until they meet inside the cycle. Then restart one pointer at `head` and move both 1 step at a time: they meet exactly at the cycle's entry node.
* **Core Concept:** the distance from `head` to the entry equals the distance from the meeting point to the entry, modulo the cycle length
* **When to Use This Pattern?** "Find where the loop starts" in any structure where each element has exactly one successor — linked lists, `i → nums[i]` index graphs (287), iterated functions (202 Happy Number).
* **Mistakes to Avoid:**
  * Returning the meeting point — it is somewhere inside the cycle, not necessarily the entry.
  * Comparing `slow.val == fast.val`: values repeat; compare node identity.
  * Forgetting the no-cycle exit (`fast` or `fast.next` becomes `None`), including the empty list.

## 🔹 Optimization Path

* **Brute Force:** walk the list storing every visited node in a set; the first node seen twice is the entry — O(n) time, O(n) space.
* **Optimized Solution:** Floyd's two phases — O(n) time, O(1) space (the follow-up).
* **Further Improvements Possible?** No; every node may have to be visited once.

## 🔹 Solution Breakdown

* **Optimal Approach:** phase 1 finds a meeting node (or proves there is no cycle); phase 2 walks `head` and the meeting node forward together until they coincide.
* **Why This Works?** Let `a` = steps from `head` to the entry, `b` = steps from the entry to the meeting point, `c` = cycle length. At the meeting `slow` has walked `a + b`, `fast` has walked `2(a + b)`, and the difference is a whole number of laps: `a + b = k·c`. So `a = k·c − b`: walking `a` steps from the meeting point lands on the entry, which is also where a pointer from `head` arrives after `a` steps.
* **Edge Cases Considered:**
  * Empty list or a single node without a self-loop → `None`.
  * Cycle through the head (`pos = 0`) → `a = 0`, phase 2 returns immediately.
  * Single node pointing to itself.

## 🔹 Tricks & Patterns Used

* **Two-phase Floyd:** phase 1 detects, phase 2 locates — the second phase costs nothing extra in space.
* **Identity over value:** `is` comparisons on nodes, never on `val`.

## 🔹 Alternative Data Structures

* A `set` of visited nodes — simplest, but O(n) memory.
* Brent's algorithm — fewer pointer moves, also O(1) space; finds the cycle length first.

## 🔹 Complexity Analysis

* **Time Complexity:** O(n) — `slow` meets `fast` within `c` steps of entering the cycle, and phase 2 walks exactly `a` steps (`a < n`)
* **Space Complexity:** O(1)

## 🔹 Code Snippet (Brute Force)

```python
from typing import Optional


class Solution:
    def detectCycle(self, head: Optional[ListNode]) -> Optional[ListNode]:
        seen = set()
        node = head
        while node:
            if node in seen:
                return node
            seen.add(node)
            node = node.next
        return None
```

## 🔹 Code Snippet (Optimized)

```python
from typing import Optional


class Solution:
    def detectCycle(self, head: Optional[ListNode]) -> Optional[ListNode]:
        slow = fast = head
        while fast and fast.next:
            slow, fast = slow.next, fast.next.next
            if slow is fast:
                # head and the meeting point are equally far from the entry (mod cycle length)
                finder = head
                while finder is not slow:
                    finder, slow = finder.next, slow.next
                return finder
        return None
```
