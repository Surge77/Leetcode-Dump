# 278. First Bad Version

**🔗 Link:** [LeetCode 278](https://leetcode.com/problems/first-bad-version/)
**🟢 Status:** 🔄 Need Review


## 🔹 Problem Statement

Versions `1..n` are built on each other, so once a version is bad every later one is bad too. Given the API `isBadVersion(version)`, find the first bad version using as few API calls as possible.

* **Example:** `n = 5, bad = 4` → `4`
* **Constraints:** `1 ≤ bad ≤ n ≤ 2^31 - 1`

## 🔹 Quick Breakdown

* **Difficulty Level:** Easy
* **Main Approach:** **Binary search on a monotone predicate.** `isBadVersion` is `False…False True…True`; find the first `True`. If `mid` is bad the answer is `mid` or earlier (`hi = mid`), otherwise it is after `mid` (`lo = mid + 1`).
* **Core Concept:** lower-bound search — shrink to the boundary instead of stopping at the first hit
* **When to Use This Pattern?** A yes/no check that flips exactly once across a sorted range, and each check is expensive (here an API call).
* **Mistakes to Avoid:**
  * `mid = (lo + hi) // 2` overflows in 32-bit languages when `n` is near 2³¹ — write `lo + (hi - lo) // 2` (harmless in Python, but a habit worth keeping).
  * Returning as soon as `isBadVersion(mid)` is true: an earlier bad version may exist.
  * Using `hi = mid - 1` on a bad `mid` — that would discard the candidate.

## 🔹 Optimization Path

* **Brute Force:** call `isBadVersion` for `1, 2, 3, …` until it returns true — up to `n` API calls.
* **Optimized Solution:** binary search — about `log₂ n` calls (≤ 31 for `n ≤ 2³¹ - 1`).
* **Further Improvements Possible?** No; `log n` calls is the information-theoretic minimum for a single threshold.

## 🔹 Solution Breakdown

* **Optimal Approach:** `lo, hi = 1, n`; while `lo < hi`: probe `mid`; bad → `hi = mid`, good → `lo = mid + 1`. Return `lo`.
* **Why This Works?** Invariant: the first bad version always lies in `[lo, hi]`. A bad `mid` keeps it in `[lo, mid]`, a good `mid` proves it is in `[mid + 1, hi]`. The interval shrinks every step and ends with `lo == hi`.
* **Edge Cases Considered:**
  * `n = 1` → the loop never runs, answer `1` (a bad version is guaranteed to exist).
  * First version is the bad one → `hi` keeps moving left to `1`.
  * Only the last version is bad → `lo` climbs to `n`.

## 🔹 Tricks & Patterns Used

* **Half-open style `while lo < hi`** with `hi = mid`: never needs a post-loop check.
* **Overflow-safe midpoint** `lo + (hi - lo) // 2`.

## 🔹 Alternative Data Structures

* None needed. A galloping (exponential) search helps only when `n` is unknown.

* **Time Complexity:** O(log n) API calls
* **Space Complexity:** O(1)

## 🔹 Code Snippet (Brute Force)

```python
# isBadVersion(version: int) -> bool is provided by LeetCode
class Solution:
    def firstBadVersion(self, n: int) -> int:
        for version in range(1, n + 1):
            if isBadVersion(version):
                return version
        return n
```

## 🔹 Code Snippet (Optimized)

```python
# isBadVersion(version: int) -> bool is provided by LeetCode
class Solution:
    def firstBadVersion(self, n: int) -> int:
        lo, hi = 1, n
        while lo < hi:
            mid = lo + (hi - lo) // 2
            if isBadVersion(mid):
                hi = mid  # mid itself may be the first bad version
            else:
                lo = mid + 1
        return lo
```
