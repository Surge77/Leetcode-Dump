# 860. Lemonade Change

**🔗 Link:** [LeetCode 860](https://leetcode.com/problems/lemonade-change/)
**🟢 Status:** 🔄 Need Review


## 🔹 Problem Statement

Lemonade costs $5 and customers queue up in the given order, each buying one and paying with a $5, $10 or $20 bill. You start with no money and must hand back exact change using only bills you already collected. Return whether every customer can be served.

* **Example:** `bills = [5,5,5,10,20]` → `true`
* **Constraints:** `1 ≤ bills.length ≤ 10^5`, each `bills[i]` is 5, 10 or 20.

## 🔹 Quick Breakdown

* **Difficulty Level:** Easy
* **Main Approach:** **Count $5 and $10 bills; prefer giving $10 first.** A $5 needs no change. A $10 needs one $5. A $20 needs $15: give `10 + 5` if you have a $10, otherwise `5 + 5 + 5`. Fail the moment change can't be made.
* **Core Concept:** when two ways to pay exist, spend the less flexible bill — a $5 can pay any future change, a $10 only helps with $20s
* **When to Use This Pattern?** Coin/change simulations with a tiny fixed denomination set where one denomination dominates another in usefulness.
* **Mistakes to Avoid:**
  * Paying a $20 with three $5s while holding a $10 — fails `[5, 5, 5, 5, 10, 20, 10, 10]`, where the later $10 customers need those $5s.
  * Counting $20 bills — they are never given as change.

## 🔹 Optimization Path

* **Brute Force:** at each $20, try both ways to pay (`10 + 5` and `5 + 5 + 5`) recursively and succeed if any branch survives — O(2ⁿ).
* **Optimized Solution:** greedy simulation with two counters — O(n).
* **Further Improvements Possible?** No; every customer must be processed.

## 🔹 Solution Breakdown

* **Optimal Approach:** `fives, tens = 0, 0`; update per bill as above; return False on shortage, True at the end.
* **Why This Works?** Both payment options for $20 spend at least one $5. Option `10 + 5` leaves an extra pair of $5s instead of a $10 — and two $5s can do everything a $10 can (pay a $10's change, or form `5 + 5` towards a $20), so keeping $5s dominates. Hence the greedy choice never makes a future step fail that the other choice would pass.
* **Edge Cases Considered:**
  * First customer pays $10 or $20 → no change yet → False.
  * Only $5 bills → True.

## 🔹 Tricks & Patterns Used

* **Dominance:** if resource A can always replace resource B, spend B first.
* **Only track what is reusable:** $20s never leave the till, so they need no counter.

## 🔹 Alternative Data Structures

* A dict of denominations → counts, generalising to other bill sets (but greedy is only safe for canonical systems like this one).

## 🔹 Complexity Analysis

* **Time Complexity:** O(n), `n ≤ 10⁵`
* **Space Complexity:** O(1)

## 🔹 Code Snippet (Brute Force)

```python
from typing import List


class Solution:
    def lemonadeChange(self, bills: List[int]) -> bool:
        def serve(i: int, fives: int, tens: int) -> bool:
            if fives < 0 or tens < 0:
                return False
            if i == len(bills):
                return True
            if bills[i] == 5:
                return serve(i + 1, fives + 1, tens)
            if bills[i] == 10:
                return serve(i + 1, fives - 1, tens + 1)
            return serve(i + 1, fives - 1, tens - 1) or serve(i + 1, fives - 3, tens)

        return serve(0, 0, 0)
```

## 🔹 Code Snippet (Optimized)

```python
from typing import List


class Solution:
    def lemonadeChange(self, bills: List[int]) -> bool:
        fives = tens = 0
        for bill in bills:
            if bill == 5:
                fives += 1
            elif bill == 10:
                fives -= 1
                tens += 1
            elif tens:
                tens -= 1  # spend the $10: it is useless except for $20s, $5s are always useful
                fives -= 1
            else:
                fives -= 3
            if fives < 0:
                return False
        return True
```
